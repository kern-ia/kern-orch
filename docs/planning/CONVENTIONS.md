> snapshot for the planning pipeline: it records what the code and history actually do at

## Naming and file layout

All code, identifiers and comments are in English, without exception — source, doc comments,
test names. Internal prose documentation (`README.md`, `CLAUDE.md`, the `docs/index/` fiches)
stays in the language the team works in, which is French in practice.

One Go module, all implementation under `internal/`, one package per concern, package
directory named after the package. Files are named after what they hold (`state.go`,
`engine.go`, `subgraph.go`, `zones.go`); a package splits into several files by subject rather
than growing one large file. `main.go` at the root holds the Cobra entrypoint and nothing else.

Every package opens with a package comment stating what it owns **and its position in the
dependency direction** — for example, "it depends on graph only for the State type; the graph
engine reaches this package through its StepFunc hook, not the other way around". That second
half is the convention, not decoration.

Exported identifiers carry doc comments. Ports are declared as interfaces or function types in
`graph` and named for the role, not the implementation (`AgentRunner`, `StepFunc`,
`NudgeFunc`, `ApprovalFunc`). Constants that encode a wire value are grouped and named after
it (`StatusQueued`, `TypeTool`, `ZonePersistent`). Reserved sentinel values are declared as
named constants with the reasoning attached (`QueuedStep = -1`).

Wire-facing structs are `snake_case` in their JSON tags across every contract
(`kern.step-event`, `kern.registry`, `kern.activity`, the tool protocol), and a struct that
crosses the boundary says so in its comment. Optional wire fields use `omitempty` so an
unused field never travels.

## Code style, lint and format

`gofmt` layout throughout, tabs, standard import grouping (stdlib, then third-party and local
together). No `.golangci.yml` exists; `go vet ./...` is the only static gate and it is run by
hand.

**Comments carry the reasoning, not the mechanics.** The dominant habit is a comment that
explains a decision, its alternative and why the alternative was rejected — the dropping
report queue, the single pinned SQLite connection, the negative `QueuedStep`, the
replace-versus-merge rule in `runLevel`. Comments that restate the code are absent. This is
the most distinctive property of the codebase and the one a change is most likely to erode.

Configuration lives in `internal/config` as environment variables with defaults in code; no
tunable is hardcoded at its point of use. New behaviour that varies by deployment gets a
variable there, documented with why it is its own variable rather than derived from another.

Provisional contracts are labelled as such in the code (`PROVISIONAL CONTRACT (spec §6.4)` on
the agent-runner protocol) so nobody hardens a placeholder into a stable API by accident.

## Testing

Standard-library `testing` only — no testify, no mocking framework, no assertion helper.
Tests are co-located with the code under test, `foo_test.go` beside `foo.go`, in the same
package (white-box).

Test names read as behaviour sentences: `TestStateCloneIsDeepIsolated`,
`TestPublisherEmitsTheRegistryFixture`, `TestRootHasExpectedSubcommands`. Assertions are
explicit `if` conditions with `t.Fatalf` and a `got, want` message naming both values. Table-
driven tests and subtests are not used; each case is its own top-level function.

Wire contracts are pinned as JSON fixtures under `contracts/` and asserted against, so a
contract change is a visible fixture diff.

`go test ./...` must be green before a change is merged, alongside `go build ./...` and
`go vet ./...`. Coverage is not measured and `-race` is not part of the routine, which is a
known gap given the engine runs a goroutine per frontier node.

## Error handling

Errors are values, wrapped with `%w` and prefixed by the package that raised them
(`fmt.Errorf("checkpoint: save: %w", err)`). The prefix is the package name, consistently.
Sentinel errors are exported package-level `errors.New` values named `Err…`
(`ErrEmptyRunID`, `ErrNoPendingDecision`).

A custom error type appears when the failure carries information a string would throw away —
`graph.LevelError` holds every failed node in a level, with `Error()` preserving the previous
message and `Unwrap()` keeping `errors.Is`/`errors.As` working against the cause.

**Failures report what completed, not just what broke.** The engine waits for the whole level
before returning, so it collects every failure rather than surfacing the first and going
silent about the rest.

**Observability never fails a run.** The reporting hook writes its own errors to stderr and
returns `nil`; a broken sink cannot abort or slow a graph.

An ignored error is rare and always explained in a comment naming the only failure mode it can
have (the ad-hoc `ALTER TABLE` in the SQLite store is the one instance).

**Misconfiguration fails loud.** A graph referencing an unconfigured builtin errors rather
than dropping messages silently; `serve` refuses to bind a public address without a token.

## Commits and branches

Conventional Commits: `type(scope): short summary`, with the body explaining the *why*. Types
in use: `feat`, `fix`, `docs`, `test`, `chore`, `merge`. Scopes are optional and name the
subsystem (`feat(daemon):`, `feat(courtage):`).

**No tool signature in commit messages** — no `Co-Authored-By`, no `Claude-Session`, no
equivalent trailer. The git author is enough.

Branches: `main` (stable, protected), `dev` (integration, protected), and working branches
named `feature/<slug>`, `fix/<slug>`, `chore/<slug>`, `docs/<slug>`, `test/<slug>`. Merging
into `dev` uses `--no-ff`, producing a merge commit per branch.

Pipeline branches, Pull Requests, milestones and issues land on `origin` —
`git@github.com:kern-ia/Kern-Orch.git` ([decision](/mapping/03-doc-push-remote.md)).

Two open gaps are recorded rather than hidden: the GitHub default branch is still `dev` rather
than `main`, and the module path `github.com/yoann/kern-orch` diverges from the org repository
name pending an org-level decision.

## Review

**Every change goes through a Pull Request, one subject per PR, linked to the issue it
resolves; never a direct push or a local merge pushed to `dev`.** The history at this commit
shows the opposite — local `--no-ff` merges pushed straight to `dev`, with a single PR ever
opened — and the root conventions file names that a gap it commits to closing. The PR flow is
the recorded standard ([decision](/mapping/02-pr-flow-vs-observed-practice.md)).

Because no CI workflow exists, "checks pass before merge" currently means locally-run
`go build ./...`, `go vet ./...` and `go test ./...`, reported in the PR. Adding
`.github/workflows/ci.yml` (build, `go test -race -cover`, `golangci-lint`) is the outstanding
item, modelled on `kern-anon`'s.

A PR states its semver impact, carries no real personal data, and uses the PR template
inherited from `kern-ia/.github`. Any change that reverses the `graph` ← infrastructure
dependency direction must justify it explicitly in the PR description.

**Documentation ships with the change.** Every merged feature gets an OKF fiche at
`docs/index/<nnnn>-<feature>.md` — frontmatter with `id`, `feature`, `branch`, `status`,
`files`, `tests` and dated `decisions`, then a body of what / why / verified-for-real, kept
short. `CLAUDE.md`'s command list stays synchronised with the real CLI. There is no
`CHANGELOG.md`: release notes live in the annotated tag, per org convention.
